# Design & UI Standards ("de-slop" audit)
Source: user supplied a full "redesign-existing-projects" skill document and instructed "make de-slop the UI" — treat this audit as the binding standard for all UI/frontend work.

- All UI work must actively remove generic AI design fingerprints: purple/blue "AI gradient" aesthetic, Inter-everywhere, 3 equal card columns, centered-symmetric everything, loud rainbow status pills, sun/moon toggles, accordion FAQs, avatar circles. Scan → diagnose (list every generic pattern) → fix; never rewrite from scratch. Confidence: 0.9
- Typography: use fonts with character (Geist, Outfit, Cabinet Grotesk, Satoshi; serif header + sans body for editorial) — never browser defaults or Inter/Arial everywhere. Sentence case headers (not Title Case), body width ~65ch, negative tracking on display text, Medium/SemiBold for hierarchy, tabular-nums (font-variant-numeric) on any live-updating numbers, text-wrap: balance for orphans. Confidence: 0.9
- Color: one accent color max, saturation below 80%, a single gray family (warm OR cool, never mixed), off-black/tinted dark instead of pure #000, tinted colored shadows, subtle noise/grain/texture over flat surfaces, no random dark sections inside light pages. Status indicators: neutral pills + one colored dot (Linear-style), not saturated filled pills. Confidence: 0.9
- Interactivity is not optional: hover states, active press feedback (active:scale-[0.98] / translateY(1px)), 200–300ms transitions, visible :focus-visible ring (accessibility), prefers-reduced-motion respected, animate transform/opacity only, skeleton loaders instead of spinners, designed empty and error states, never window.alert(), no dead # links, styled active nav item. Confidence: 0.9
- Copy de-slop: never use "Elevate", "Seamless", "Unleash", "Next-Gen", "Game-changer", "Delve", "Tapestry", "In the world of..."; no exclamation marks in success messages; direct active-voice errors ("We couldn't save your changes"); realistic messy data (47.2%, $99.00, +1 (312) 847-1928 — not 50%, $100.00); real draft copy, never Lorem Ipsum; diverse believable names and randomized dates. Confidence: 0.9
- Layout: break symmetry (asymmetric grids, zig-zag, left-aligned headers over centered content), max-width container ~1200–1440px, min-height: 100dvh (never 100vh), CSS Grid over flexbox percentage math, generous whitespace ("double the spacing"), align baselines/buttons across side-by-side cards (CTAs pinned to card bottoms), varied border-radius, optical 1–2px corrections over mathematical centering. Confidence: 0.85
- Icons/imagery: avoid default AI choices — not Lucide/Feather exclusively (prefer Phosphor, Heroicons, custom), no cliche metaphors (rocket=launch, shield=security), consistent stroke widths, branded favicon, unique avatars per person, real/candid imagery over uncanny stock photos. Confidence: 0.9
- Method when upgrading existing projects: work with the existing stack, never migrate frameworks or styling libraries; small targeted reviewable changes, test after every change; check package.json before any new import and Tailwind version (v3 vs v4) before touching config. Confidence: 0.9
- Apply fixes in priority order for max impact/min risk: font swap → color cleanup → hover/active states → layout & spacing → replace generic components → add loading/empty/error states → typography polish. Cover the usual AI omissions: legal links, back navigation, custom 404, form validation, skip-to-content link, meta/og tags, favicon. Confidence: 0.9
- Branding assets implementation pattern (explicitly requested: "work on favicon and Open Graph, branding matters") for Next.js App Router: delete the default `favicon.ico` and ship `app/icon.svg` matching the header logo mark; generate the OG card in code via `app/opengraph-image.tsx` + `next/og` (1200×630, brand palette/typography) so it's not a static image to maintain; wire full metadata — title template `%s — App`, `metadataBase` from `NEXT_PUBLIC_APP_URL` (add it to `.env.example`), `twitter: summary_large_image`, explicit `icons` config. Satori (`next/og`) constraint learned from a real build failure: every div with multiple children — including a text node mixed with an element like `<br/>` — must declare explicit `display: flex` or the production build fails during OG prerender; prefer a flex column of child divs over `<br/>` for multi-line headlines. Confidence: 0.85
- Navigation and CTAs must be state-aware, never hardcoded: user caught that every signed-in landing-page CTA pointed at `/onboarding`, so already-onboarded users got "Open Doppel" → onboarding flash → dashboard redirect, plus a "Continue onboarding" label while already done. Rule: entry points query the real auth/onboarding state and route accordingly (onboarded → `/dashboard`, new → `/onboarding`); while auth/profile resolves, render a dimmed neutral placeholder instead of a wrong link that flashes; the redirect for direct URL visits stays only as a safety net, never the primary navigation path. Implement once as a reusable component with per-surface label props and swap it into every signed-in touchpoint (nav, hero, teasers), not just the one the user clicked. Confidence: 0.85
- Metadata assets must be public routes when auth middleware is present: Clerk's `proxy.ts` was protecting `/opengraph-image`, so crawlers/preview extensions fetching the card got the sign-in HTML redirect instead of the PNG (page title/description still showed because those meta tags live on the page — only the image silently fails). Fix: add `/opengraph-image(.*)`, `/icon.svg`, `/favicon.ico` to the `createRouteMatcher` public routes. Verify by curling the image route and checking `content_type` is `image/*` (`200 image/png, 85 KB`), not just that page meta tags exist; note OG preview extensions often refuse to render localhost images regardless — full visual verification needs a deployed URL or a tunnel (ngrok). Confidence: 0.85
- For agent/chat products, the user wants the modern chat-app layout architecture (Gemini/ChatGPT pattern), NOT a dashboard of cards: fixed-width left sidebar (~280px, and explicitly desktop-collapsible per user request "make the sidebar toggelable, I can collapse and open it" — a floating panel-icon toggle button pinned at the workspace's top-left, width animating 280px ↔ 0 over 200ms with the border collapsing too, header padding adjusted so the floating button never overlaps the status pill, mobile untouched since its top bar replaces the sidebar) holding brand + live running-count indicator, a prominent primary "New Session" button, a scrollable session-history list, and a pinned user-profile footer; the main canvas is one centered column (max ~850px) with two states — State A (new session): vertically/horizontally centered hero greeting above a wide command bar with actions embedded in it (Run button, char counter, profile selector, example chips); State B (active session): session header (status pill, timestamps, stop control), the timeline, the result, and a sticky bottom follow-up input bar. This overrides the general "break symmetry / 1200–1440px" layout default for app surfaces of this kind. Confidence: 0.85
- Chat-app default landing state (explicit user demand after the dashboard auto-opened their latest session): opening the app must always land on the fresh new-session composer (State A), never auto-select/restore the most recent or previous session — history items open only on explicit user click, and submitting a prompt jumps to that run's live view. Default to a neutral starting state; never silently resume where the user last was. Confidence: 0.85
- Layout refactor ≠ visual retheme: when the user requests a structural/UI-layout change, strictly retain the existing visual design language — light theme, sharp high-contrast 1px borders, rounded corner radius, crisp monochrome typography, existing badge styles. Never import the reference app's aesthetic while borrowing its layout — explicitly banned: Gemini's dark palette, blue radial gradients, subtle shadows. Confidence: 0.85
- Organizing dense multi-domain pages (explicit user request: "make it well organized" for the settings page): restructure one-long-scroll pages into tabs with a sensible default tab and count badges (e.g. Logins / Profile / Markdown context), each tab made of grouped titled cards with one-line helper copy per field group; pin the primary action ("Save changes") in a sticky bottom bar on long tabs instead of burying it below a tall textarea; fold secondary/technical content ("How login persists", stored-connection lists) into collapsed `<details>` disclosures rather than permanent on-page noise. Reorganization is structure-only — every existing behavior (polling, uploads, field sync) must stay wired, and loading states become layout-matched skeletons. Confidence: 0.8
- User-facing pages must contain zero developer-facing noise: dev architecture boxes, SDK/API lecture copy (docs.getsolari.com, `client.launch(...)` snippets), and all-caps technical section labels are slop inside a product page — remove them outright, or keep genuinely useful raw IDs behind an explicit "Show details" disclosure. Marketing/hero content follows the same rule: show user outcomes and benefit language ("1 email sent — approved by you", "Real browser, logged in as you", "Watch every action live", "Stop anytime"), never stack names or infra capabilities (Next.js/Convex/Solari badges, "Stealth Chrome via Solari", "VNC replay") — user explicitly asked to "remove irrelevant things for the customer". Confidence: 0.85
- Text inputs must grow with their content: a fixed single-line `<input>` that clips long text is a defect the user immediately flags ("When I type long passages, It doesn't expand along with the text, text is just cut"). Composer pattern: auto-resizing `<textarea>` (rows=1, height auto→scrollHeight on every change, capped ~max-h-[200px], resize-none), Enter submits / Shift+Enter adds a newline (with the hint visible next to the char counter), and the Run/Send button stays bottom-aligned (`items-end`) as the box grows. Confidence: 0.9
- Submitting an action must give instant visible acceptance — "as soon as I hit send, I want instant response that my request has been accepted." Never leave the primary action blocked on the network round-trip: optimistically switch to a pending state the moment the button is pressed (green ✓ "Task accepted" + "Booting your sandbox and attaching your saved logins" copy, the submitted prompt rendered as the session title, skeleton timeline, disabled follow-up bar) while the real request runs in the background, then hand off to the live view when the session ID arrives; on failure restore the user's typed text into the composer with the error shown so nothing is lost. Confidence: 0.9
- Marketing pages for this product need an honest FAQ answering the questions a skeptical first-time user actually has — user explicitly requested it and seeded the topics ("will my accound be banned if I use them to automate, what is the pricing, and other questions that may arise"). Cover at minimum: account-ban risk, pricing, credential privacy ("do you see my passwords"), supported sites, expired-login recovery, mid-task stopping. Format follows the user's explicit spec, not the agent's de-slop default — the conversion landing-page brief explicitly demanded a "6-item accordion" (bans, pricing/beta status, password privacy, cancellation), so the FAQ ships as a native `<details>` accordion with a rotating chevron; an explicit user spec overrides the standing accordion ban. Answer honestly rather than reassuring ("Any automation carries some risk — no honest tool can promise zero") — candor over canned comfort. Confidence: 0.85
- Text fields must never show a focus outline inside them — user explicitly flagged the global `:focus-visible` outline as a "black outline inside the chat input" and demanded its removal. Exception to the general visible-focus rule: `input`, `textarea`, and `select` get `outline: none`; they signal focus through their container's border/ring change instead. The global keyboard-accessibility outline stays for non-text controls (buttons, links, non-input widgets). Confidence: 0.85
- The user's explicit structured brief overrides the standing de-slop bans: the conversion landing-page spec deliberately requested patterns the audit bans as generic slop (3-column equal card grid, FAQ accordion, centered dark CTA panel) and they were built exactly as specified. Rule: the ban list governs agent-initiated design choices only — when the user's own spec names a pattern, implement it as written. Confidence: 0.85
- Doppel marketing/landing design language (user's explicit design direction): clean light theme (white / #fafaf9 surfaces), subtle background grid built from 32px 1px linear-gradients at ~3% opacity (used on both the light hero and the dark CTA band), crisp dark stone typography with tight negative tracking, rounded card containers (rounded-2xl up to 24px), small status tags (BETA pill, running step counters), and high-contrast dark pill CTAs (stone-900 → hover:bg-black, active:scale-[0.98]). Confidence: 0.85
- Conversion anatomy for the Doppel landing page (treat as the standing structure when editing it): hero headline is the user's original brand line ("Your professional doppelgänger." with the gradient on the second line), and the subheadline frames the product as general-purpose browser automation (uses Gmail, LinkedIn, X and any website the way you do; "If a browser can do it, Doppel can do it while you watch"): the user explicitly rejected the job-automation/outreach-narrowed rewrite and demanded the original hero kept; preserve original user-approved copy instead of overwriting it on later passes, risk-reversal microcopy directly under the primary CTA ("Free during private beta • No credit card required • 30-second setup"), 3-step numbered how-it-works, 3-column capabilities grid (icon + <5-word title + one-sentence benefit), 6-item FAQ accordion, and waitlist email capture at two points (hero for signed-out visitors + final dark CTA band) — page flow: hero → How it works → Capabilities → FAQ → waitlist CTA → footer. Post-render trim overrides the brief: after seeing the page live, the user explicitly deleted two brief-specified sections — the social proof bar (platform strip + metric card) and the red-vs-green before/after comparison (~4 hours → ~4 minutes) — plus their now-unused Check/Cross helper components; those sections are gone from the standing structure. Confidence: 0.85
- Never fabricate social-proof claims or usage metrics on marketing pages: the user removed the invented "10,000+ tasks automated safely" metric card (a number the agent had already flagged as an unsubstantiated claim) along with the entire platform strip. Don't ship invented customer counts, task totals, or endorsement-style stats the product can't yet prove — omit social proof entirely or use only verifiable statements. Confidence: 0.75
- No fake live/activity theatrics on user-facing pages: the user demanded the frontpage be deslopped with no pulsing green light and no "live now" or "currently active" vibe. Strip every `animate-pulse` dot and animated status chip that implies a running connection when it is decorative (static stone dot in the beta badge, plain "logged in as you" chip without the "live" tag, neutral "step 4/15" pill instead of a green "running" one). Reserve animated live indicators for UI that is genuinely streaming. Confidence: 0.9
- Default body text is too small at `text-sm` (14px) for this user: after the landing-page review they asked to "increase the font size a little". Standing sizing when writing/maintaining their UI: body/paragraph copy ≥15px, card titles and FAQ questions ~16px, hero subheadline ~18px, section heading lines ~24px. Keep genuinely small UI chrome (nav links, buttons, badges) and deliberately miniature mock/terminal text at its original size; the bump targets reading copy only. Confidence: 0.7
